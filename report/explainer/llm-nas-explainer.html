0Background

The paper and our two questions

What LLM-NAS does. It searches for small neural networks that are both accurate and fast on a given chip. The candidates are cells from NAS-Bench-201: each cell has six connections, and each connection is one of five operations, so there are 15,625 possible cells. Instead of changing cells at random, as an evolutionary algorithm would, the method asks GPT-4.1 to propose new cells from the best ones found so far. It also has the model keep a running list of design rules, the knowledge base.

Two other parts matter. The space is split into six niches by how many 3×3 convolutions a cell has, so the search covers simple and complex designs alike. And no network is trained. Accuracy comes from a predictor built on cheap "zero-cost" scores, and latency comes from a table of measurements on six chips (HW-NAS-Bench).

What it claims. Fronts close to the best possible (hypervolume 0.997 on CIFAR-10, Edge GPU) from 120 API calls and about 3 minutes per search, far cheaper than methods that train networks. The authors did not release code.

Our two questions

  1. With the same evaluator and the same budget, does the LLM find better designs than a plain, non-LLM search would?
  2. Does the LLM bring design knowledge that the search would not have found by itself?
Why this framing

The paper compares itself with methods that train networks for days. Much of its saving comes from not training at all, which any search algorithm can do. To credit the LLM, it has to beat other searches that use the same shortcut.

1Done

Objective 1: a reproduction anyone can re-run

Can every number be regenerated later, without paying for API calls again?

What we did

  • Rebuilt the method from the paper's text, its Algorithm 1 and the prompts in its Appendix E, as a Python package.
  • Put every setting in one file. Each setting is tagged [paper] if the paper states it, or [assumed] if we had to choose. There are 13 assumed choices. The main ones are 5 starting cells per niche, 4 children per call, at most 6 parents shown, and temperature 0.7.
  • Gave each run a folder named after a fingerprint of its settings. A finished run is never recomputed, and changing a setting creates a new folder instead of overwriting.
  • Logged every prompt and reply. Any LLM search can be replayed exactly, offline and at no cost.
  • Wrote 60 automated tests that run on synthetic data with a fake LLM.
Why it mattered later

The replay logs made the duplicate analysis in Section 7 free: we re-read 720 GPT-4.1 calls without calling the API. They also let us show that the new duplicate-fix code changes nothing when switched off. Five archived runs, including real GPT-4.1 and DeepSeek searches, reproduced exactly.

2Done

Objective 2: is our data the paper's data?

Before comparing results, do the benchmark tables we built match what the paper used?

What we did

We merged three public sources into one table per dataset: latency from HW-NAS-Bench, zero-cost scores from NAS-Bench-Suite-Zero, and accuracy from NATS-Bench. Then we checked the result against every number the paper prints.

What we found

  • 11 of the 12 architectures in the paper's Table 2 exist in the benchmark with matching accuracy and latency. The twelfth (94.37% at 4.35 ms on Edge GPU) does not exist. The same row is printed for another method, so it is probably a copying error in the paper.
  • A benchmark flaw. 4,699 cells (30%) have an Edge TPU latency of −1, meaning they failed to compile for that chip. Treated as real numbers, they look like free, instant models and drag every method's Edge TPU score down to about 0.2. We treat them as impossible on that chip. The paper does not say what it did.
  • Our accuracy predictor ranks cells better than the paper's: a rank correlation of 0.96 against about 0.90. It helps every method equally.
What it means

The data matches, so differences from the paper come from the method or the scoring, not from the data. The Edge TPU flaw has to be handled by anyone who uses this benchmark. As far as we found, no paper mentions it.

Objective 3: the headline result

On the paper's main setting (CIFAR-10, Edge GPU), do we get its score, and does swapping the LLM change it?

What we ran

GPT-4.1, the paper's model, plus Claude Opus 5.5, DeepSeek-Coder-V2-16B and Qwen2.5-7B. The last two ran on your laptop GPU at no API cost. We compared them with two non-LLM controls that use the same niches and the same predictor: PEA (random changes to the parents) and random sampling inside each niche.

Objective 5: is the scoring rule fair?

The paper does not say exactly how it computes hypervolume. Does the choice change who wins?

Hypervolume is the area between a set of designs and a reference point. We report it as a share of the area the true best front would cover, so 1.0 is perfect.

What we found

One useless cell distorts the scale. On Edge GPU the true best front ends in a "network" whose input never reaches its output. It answers at chance level (10% accuracy) but runs fastest (0.50 ms), so it sits on the front. Scores are stretched between the best and worst points of the front, so this one cell squeezes all sensible designs into the top 9% of the accuracy scale. That compresses the differences between methods.

Removing cells below 80% accuracy changes the order on Edge GPU:

  • With the floor, Claude Opus is the only LLM ahead of the controls, at about $11 per search. GPT-4.1 falls well behind them.
  • The paper's near-perfect scores (0.996–0.997) appear on exactly the three devices whose true front has such a cell. On the other three it reports 0.93–0.96. This fits the effect but does not prove the paper scored that way.
  • We re-scored every run under 16 plausible scoring rules. GPT-4.1 ranks 6th of 9 methods under every one of them, so its position does not depend on the rule.
What it means

Comparing HV across papers in this field is unreliable until authors state their scoring rule. Our conclusions about GPT-4.1 do not depend on the rule. Claude Opus's advantage does.

Objective 6: is the LLM worth it?

With the same evaluator, does the LLM find better fronts, or find them with fewer evaluations, than a cheap search?

Equal evaluations

The LLM runs evaluate fewer cells, because many of their proposals are rejected. To compare fairly, we read each control's score at the point where it had evaluated as many cells as GPT-4.1 had (145 on average).

After 145 evaluationsMean HV, six devices
Regularised evolution0.960
NSGA-II0.949
PEA0.944
Random sampling0.930
GPT-4.10.928

At the same number of evaluations, GPT-4.1 is level with random sampling and below the evolutionary methods.

Is the gap real or noise?

We tested whether GPT-4.1 is worse than each control with a cautious test that treats the six devices as six data points. With six devices the smallest possible p-value is 0.016. GPT-4.1 reached it against PEA, NSGA-II and regularised evolution under all 16 scoring rules. We also checked that a smaller or larger predictor does not change the order of the controls.

What it costs

A GPT-4.1 search costs $0.80–0.88 and takes about 8 minutes. The controls cost nothing and finish in about a second.

Where an LLM could still pay off (not tested)

Expensive evaluations

Here an evaluation takes a millisecond. If each one meant training a network, saving evaluations would matter.

Open-ended spaces

When designs are code, writing a random mutation is hard and a text interface helps.

Explanations

The rules and rationales are readable. Only Claude Opus backed its rules with its own measurements.

Larger spaces

15,625 cells is small enough for random search to do well. A good prior might matter more in a far larger space.

What it means

On this benchmark the paper's cost saving comes from skipping training, which the free controls also do. The LLM contributes readable rules and a text interface, not better fronts. The NSGA-II and regularised-evolution runs were added after the paper's Section 5 was written, so that section still needs updating.

Objective 7: where the budget goes

Why do the LLM runs evaluate so few cells, and what does that cost them?

The arithmetic

The paper's budget is 120 calls: 60 update the knowledge base and 60 ask for 4 new cells each, so 240 cells are requested. A rejected proposal is not replaced. GPT-4.1 therefore evaluates about 145 cells (30 starting cells plus the accepted ones), against 270 for NSGA-II and regularised evolution, which keep generating until the budget is full.

Two different failures

  • Copying what they are shown. 41% of DeepSeek's proposals and 33% of Haiku's are a parent from the same prompt, returned unchanged.
  • Forgetting what they tried. GPT-4.1 rarely copies a parent (6%). Most of its duplicates (32% of all its proposals) are cells it had already seen 3–5 generations earlier, which have since dropped out of the prompt. Each call starts fresh, so the model cannot know the cell was tried.
  • For GPT-4.1 the duplicate rate climbs from 3% in generation 1 to 65% by generations 8–10. Running out of space is not the cause: at the time of a proposal, at most 4.5% of a niche had been evaluated on average.
What it means

Part of the LLM's lower score comes from evaluating fewer cells, not only from worse proposals. To our knowledge this is the first exact count of duplicate LLM proposals in a fully listed search space, broken down by source. It is now a section of the paper, "Where the budget goes".

Objective 8: the duplicate-fix test

If we stop the waste, does GPT-4.1 catch up with the controls? This separates "evaluates fewer cells" from "proposes worse cells".

Rules written before any result

We wrote the test into PREREGISTRATION_duplicate_fix.md and committed it before writing any code. It fixes in advance which runs count, what is measured, and what would count as a win or a loss, so the result cannot be tuned afterwards. Every outcome gets reported, including "no better" and "worse".

The two fixes

Fix 1: show the history

Each request lists every cell already evaluated in the niche (at most 45), with an instruction not to repeat them. This targets GPT-4.1's forgetting.

Fix 2: ask again

When children are rejected, the model is asked again for only the missing ones, told which were rejected and why. At most 5 retries. A slot still empty after that stays empty and is never filled with a random cell.

Each arm is GPT-4.1, CIFAR-10, all six devices. Arm A is read at two points: after 270 evaluations (equal budget) and after 120 (where a good prior should help most).

How a verdict is reached

For each device, the margin is twice the control's spread over its 10 seeds, or 0.010 if that is larger. A difference smaller than the margin could be luck.

  • Better: GPT-4.1 beats the control by more than the margin on at least 5 of 6 devices, and the six-device test gives p ≤ 0.05.
  • Worse: it trails by more than the margin on at least 5 of 6 devices, or the test gives p ≤ 0.05 in that direction.
  • Parity: anything else.

Separately, the fixes count as working if arm A reaches at least 265 evaluations on every device and its duplicate rate falls at least 20 points, from 42.7% to 22.7% or less.

Done so far (all free)

  • Both fixes are built as switches that are off by default. With them off, results are identical to before.
  • Tested with a fake LLM, then frozen at commit 754bc79, with that ID written into the pre-registration. The prompt wording can no longer change.
  • Amendment 1, dated and recorded: in a dry run, PEA with refill could fill only 217–265 of its 270 slots, because the near neighbours of a niche's few parents run out. It now falls back to a random new cell after 50 failed draws, as NSGA-II and regularised evolution already do. The LLM arms are still never padded.
  • All 240 control runs are finished. The analysis runs as one command, python -m llmnas dupfix.

The problem found, and amendment 2

Hypervolume cannot exceed 1. On Edge GPU, Raspberry Pi 4 and Pixel 3 the controls already score 0.991–0.995, so beating them by the 0.010 minimum would need a score above 1. With only 3 devices left where a win is possible, "at least 5 of 6" can never be met. As written, the test could find GPT-4.1 worse but never better.

Proposed amendment 2: count only devices where beating the margin is possible, require a win on all of them (at least 3), and keep the six-device significance test. "Worse" and "Parity" stay as they are. The decisive devices become the ones where the controls have room to improve:

What we expect, written down in advance

The fixes will cut the waste and fill the budget. GPT-4.1 will then be level with PEA and random sampling and still below NSGA-II and regularised evolution. As a preview, the existing GPT-4.1 runs read at 120 evaluations are already level with PEA with refill, random sampling and NSGA-II, and worse than regularised evolution (p = 0.016). These are not the test results.

If GPT-4.1 catches up

Its earlier deficit was mainly the wasted budget, and the paper's framework, not the LLM, was the weak point.

If it stays level or below

The negative result stands even with a full budget: on this benchmark its proposals are no better than random changes.

If the fixes fail to fill the budget

That is itself a finding about how well the model follows instructions, and the equal-budget question stays open.

GReference

Glossary

Cell
One candidate network design in NAS-Bench-201: six connections, each with one of five operations. 15,625 in total.
Pareto front
The designs for which nothing else is both faster and more accurate. The "true front" is the best possible one, computed from the full benchmark.
Hypervolume (HV)
The area covered by a set of designs up to a reference point, as a share of the true front's area. 1.0 is perfect; higher is better.
IGD
Average distance from the true front to the nearest found design. Lower is better.
Niche
One of six slices of the space, by number of 3×3 convolutions. Each niche is searched separately.
Operator
The step that makes new designs from old ones. LLM-NAS uses GPT-4.1; evolutionary search uses random mutation and crossover.
PEA
The paper's own ablation: the same framework with random operators instead of the LLM. "PEA with refill" redraws rejected children.
NSGA-II, regularised evolution
Two standard evolutionary algorithms for this kind of problem. We run them with the same predictor and 270 evaluations.
Zero-cost predictor
A model that estimates accuracy from cheap scores computed without training, so a design is scored in about a millisecond.
Seed
One independent repeat of a search with a different random start. More seeds show how much results vary by chance.
Sign-flip test
A significance test on the six per-device differences. It asks how often random signs would give a result this one-sided. With six devices, the smallest possible p-value is 1/64 = 0.016.
Margin
The smallest difference counted as real: twice the control's seed spread on that device, and at least 0.010.
Pre-registration
Writing the test and its pass/fail rules down, and committing them, before seeing results.
Degenerate cell
A cell whose input never reaches its output. It guesses at chance level but is very fast, so it can sit on the true front and distort the scale.
